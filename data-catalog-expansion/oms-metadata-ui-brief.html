Schema & metadata layers
What the sections mean—and how to structure the catalog UI

A concise reference derived from the Operational Metadata Store screenshots: two meanings of “schema,” how Overview / Technical / Business metadata differ, and whether separating business from technical metadata in a BDC-on-top view is sound.

1. What “schema” means in OMS

The product uses schema in two related ways. Both are correct; the trick is knowing which one you are looking at.

A. Snowflake namespace

In Technical metadata, fields like Database and Schema refer to where the object lives in Snowflake. Example: database marsci_acquisition_pro, schema build—the middle segment of database.schema.table.

Location · access · naming

B. Column-level structure

The collapsible Schema panel is the table structure: one row per column with name, type, description, tags, and column lineage. This is the physical / logical “data dictionary,” not the Snowflake schema name.

Columns · types · lineage
Remember: Namespace schema = folder for the table. Schema panel = list of columns and types. Same word, different planes—worth a one-line tooltip or glossary link in the UI.

2. Overview vs technical vs business metadata

Each block answers different questions for different people. Keeping them visually distinct reduces noise and matches real workflows (discovery vs operations vs governance).

Section Role Typical content Primary users
Overview Quick asset facts for trust and discovery Environment, created date, type/status, access recency, table age, creator, documentation hints Consumers, PMs, light analysts—“Can I use this?”
Technical metadata How it is built and operated Database, schema (namespace), rows, size, last altered, cost, clustering, Airflow IDs, usage metrics Data engineers, platform, FinOps, ETL owners
Business metadata Meaning, ownership, governance Owners/stewards, policies, descriptions, classification, sensitivity, segment, region Stewards, governance, compliance, analysts needing context

Merge or keep separate?

Prefer separation (sections, tabs, or strong headings)—or a very short “at a glance” summary up top with detail below. Reasons:

  • Different personas care about different fields; one flat list creates clutter.
  • Edit permissions and sensitivity often differ (e.g. cost vs business description).
  • Collapsible panels or tabs preserve scanability for mixed audiences.

A single merged block can work for a narrowly technical audience, but for engineers + analysts + stewards together, segmented layout usually wins.

3. BDC “UI on top” — business vs technical split

A stewardship-first surface (for example business-data-catalog/oms-ui-on-top.html) that defaults to descriptions, policies, and business column context while tucking types and physical detail behind a toggle is coherent and defensible.

Why it works

  • Aligns default experience with stewards and business users.
  • Lets engineers opt in to technical column fields when needed.
  • Mirrors OMS’s mental model without forcing every OMS metric onto the first screen.

What to add for balance

  • A clear path to full operational metadata for users who live in row counts, DAGs, or cost.
  • Optional one-line “at a glance” (env, owner, row count) if decisions depend on it.

One-line summary

In OMS, schema is either the Snowflake namespace or the column list; Overview / Technical / Business serve discovery, operations, and governance respectively—keep them distinct in the UI; a BDC-on-top layer that foregrounds business metadata and optionally reveals technical detail matches that story well.
