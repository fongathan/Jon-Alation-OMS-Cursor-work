Vision & problem

Today’s catalog footprint is anchored on warehouse-native objects. That misses how data is activated, segmented, and explained in downstream SaaS: reverse ETL (e.g. Hightouch), customer data platforms, lifecycle and engagement tools (e.g. Braze), and ad-hoc spreadsheets of “truth” owned by growth and product.

North star: One searchable, governed catalog that registers not only tables and pipelines, but also vendor entities, syncs, audiences, traits, and campaign touchpoints—with clear ownership and lineage to warehouse sources where applicable.

Program objectives

  1. Parity migration: Map Alation requirements (glossary, stewardship, search, lineage, policies) onto the in-house catalog.
  2. Vendor plane: Define asset types, connectors, and refresh semantics for non-warehouse systems.
  3. Cross-plane lineage: Link warehouse tables → sync jobs → vendor entities (audiences, traits, campaigns).
  4. Governance: PII classification, data contracts, and access reviews that span warehouse + SaaS.
  5. Adoption: Self-serve discovery for analysts, growth, and data engineering with clear SLAs.

Phased roadmap

  • Phase 0 — Foundation Inventory Alation usage; confirm OMS/extension architecture; vendor shortlist workshops.
  • Phase 1 — Warehouse + pipeline parity Hive, Snowflake, Databricks/Unity: documentation, ownership, lineage, policies at table/column level.
  • Phase 2 — Activation layer Ingest metadata from reverse ETL (mappings, sync frequency, destinations); surface in catalog UI.
  • Phase 3 — CDP & engagement Event catalogs, computed traits, audience definitions; link to warehouse grain where possible.
  • Phase 4 — Hardening & scale SLAs, audit exports, API for programmatic consumers, cost/usage views per connector.

Risks & mitigations

  • API sprawl: Prioritize vendors by business criticality; use a thin adapter pattern per vendor family.
  • Semantic drift: Treat vendor fields as first-class with effective-dated definitions and owners.
  • Compliance: Model residency and purpose-of-use per asset; block risky joins in the UI where needed.
