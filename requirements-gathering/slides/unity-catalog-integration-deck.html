Two complementary roles

Slide 2 of 10

Unity Catalog — execution plane

  • Permissions, audit, native lineage on Databricks assets
  • Metric Views — governed KPIs for SQL, Genie, AI/BI
  • Masking, ABAC, classification enforced at query time

Strategy: UC governs the lakehouse; our internal services federate the estate. Same metadata spine — different jobs.

Glossary vs. metrics — different jobs

Slide 5 of 10

Navigator (internal catalog)

  • Stewarded terms: definitions, synonyms, status, domain ownership
  • Links to tables & columns across all sources
  • Concepts that aren't single SQL metrics (policies, dimensions, process language)

Unity Catalog (today + roadmap)

  • Metric Views — how KPIs are calculated (SQL + agent metadata)
  • Future Glossary — announced DAIS 2026; preview coming soon
  • Valuable for Genie/agents on Databricks — should feed OMS when Generally Available (GA)
Integrate, don't duplicate: metrics layer standardizes calculation; business glossary standardizes meaning. Navigator owns vocabulary; UC owns Databricks-native metric enforcement.

Best ways to integrate with Unity Catalog

Slide 7 of 10

Architecture principles

  • Hub-and-spoke: UC = Databricks System of Record (SoR) for schemas, grants, native lineage, metric views
  • OMS = enterprise metadata store; Navigator = discovery & stewardship UX
  • One System of Record (SoR) per metadata type — no dual-writing glossary or ownership
  • Avoid metadata dual-write — pick where each attribute is authoritative

Recommended integration patterns

  • Crawl / sync UC → OMS: tables, columns, grants summary, lineage, metric view defs
  • 626 / MCI continues supply for non-Databricks sources into same OMS spine
  • Navigator surfaces UC assets in unified search with Snowflake & pipeline objects
  • When UC Glossary is Generally Available (GA): ingest into OMS — one glossary UX, not two
  • Optional: one-direction tag sync (e.g. PII) — editable in one system only
Goal: Databricks assets are first-class in our catalog; UC stays authoritative for Databricks enforcement.

External lineage & BYOL — what it is

Slide 8 of 10

What BYOL provides (Generally Available)

  • Register metadata & lineage from outside Databricks via APIs
  • Extend UC lineage graph — Salesforce, MySQL, Tableau, etc.
  • Useful for audit, impact analysis on lakehouse assets
  • Stitches upstream/downstream into UC's view

What BYOL is not

  • Not a managed enterprise catalog — you build every integration
  • Not automatic crawlers across 20+ sources (Alation / OMS supply model)
  • Not governance propagation — UC tags don't enforce in Snowflake or BI
  • Not a substitute for glossary, articles, or Navigator stewardship
BYOL narrows the lineage gap inside UC. It does not close the business catalog gap.

Problems & limits of BYOL

Slide 9 of 10
Engineering taxEvery API change, schema drift, or tool upgrade can break BYOL pipelines — ongoing maintenance, not one-time setup.
Incomplete coverageHard to match column lineage, dataflows (Airflow/dbt), BI reports, usage analytics without heavy custom work.
Latency & freshnessExternal metadata often polled or batch-loaded — not live operational picture like managed crawlers.
Governance silosDomains, certifications, PII tags in UC don't translate to Snowflake Horizon or other platforms.
Double governanceSnowflake + Databricks = two permission models unless explicitly synced — BYOL doesn't unify enforcement.
Vendor lock-in via BYOLDeepening UC as the lineage hub ties more governance context to Databricks without delivering enterprise glossary or Navigator stewardship.
Cost shift"Skip the catalog" can become headcount maintaining N BYOL integrations per source.

Practical takeaway: use BYOL to enrich UC lineage where valuable; rely on OMS + 626 for estate-wide federation — don't replace internal services with BYOL.

Strategy, talking points & asks

Slide 10 of 10

How to talk about it

  • "We're not choosing UC or our internal services — we're integrating both."
  • "UC governs the lakehouse; Navigator lets business users find and trust data everywhere."
  • "BYOL helps lineage in UC — it doesn't replace glossary, articles, or cross-platform search."
  • "We maintain connectors once in OMS — not N custom BYOL pipelines per source."

Asks

  • Endorse dual-platform strategy: UC + OMS/Navigator for Alation exit (2027, likely one-year extension)
  • Charter UC → OMS integration (crawl, lineage, metric views)
  • Define System of Record (SoR) matrix — prevent dual-write on glossary & ownership
  • Track UC Glossary Generally Available (GA) for ingestion into OMS — not a UC-only glossary program
Both platforms, one story: federated discovery and stewardship on internal services; governed execution on Databricks.
