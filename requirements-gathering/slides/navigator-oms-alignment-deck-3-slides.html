Shared vocabulary — product ownership vs platform dependency

Slide 1 of 3

The alignment line

Navigator is our product. OMS is our platform dependency.
We are not building “OMS features” — we are building a governed catalog experience that consumes OMS APIs, while governance definitions live in a separate repository Foundations does not own.

Two bullets to agree on

  • Navigator = product ownership — Data Governance owns requirements, personas, MVP scope, and roadmap (Alation migration: search, browse, glossary, asset detail).
  • OMS = platform dependency — OMS stores operational metadata and exposes APIs; we depend on it to run, but it does not define our program.
When Suman says “OMS is irrelevant” — he means governance must not be captive to Foundations’ OMS roadmap. Not that Navigator should avoid OMS entirely.

Translate the vocabulary

Product ownership (Navigator) Who decides what gets built and for whom — even if OMS devs build it and OMS APIs back it. Separate product name, entry point, and success metrics.
Platform dependency (OMS) What we depend on to ship — metadata store, graph, APIs, engineering capacity. Like an app depending on iOS: need the platform, not subordinate to its product roadmap.
Governance SoR (separate) Classifications, policies, and metrics governance live in a tool-agnostic repository — not inside OMS. OMS reads / projects those definitions onto assets.
On-top UX pattern Navigator is a dedicated business-first shell above OMS APIs — not the OMS engineering UI. Engineers keep an integrated OMS path; stewards and consumers use Navigator.

Stack (unchanged): 626 / MCI → supply · OMS → store · Navigator → governed UX · Governance Portal → phase 2.

The issue — and the architecture we need

Slide 2 of 3

Where we agree

  • Tool-agnostic governance — Governance Portal, governance metadata repository, classifications, policies, metrics, Access Manager.
  • Navigator — Catalog discovery and stewardship UX (Alation replacement).
  • Two experiences — Govern & prove (Portal) vs discover & steward (Navigator).

Where friction appears

  • Execution vs strategy — Navigator ships on OMS APIs with OMS devs; Suman’s “OMS irrelevant” framing sounds like “don’t use OMS.”
  • Foundations overlap — Data Foundations Platform PRD plans an OMS UI overhaul including Alation migration features — same surface as Navigator.
  • Unresolved “Read ?” — Does OMS read governance definitions from the repository, or do we build duplicate models?
Risk: Navigator becomes “the OMS app” — Foundations owns our roadmap and Alation exit scope.

Recommended: dual product, single spine

  • Governance Metadata Repository (Postgres) — SoR for classification definitions, policies, metrics governance. Gov App backend + Governance Portal read/write here.
  • OMS — Operational metadata store + APIs. Reads / syncs governance definitions onto catalog assets. Does not own governance SoR.
  • Navigator — Data Governance–owned UI on OMS APIs. MVP now: search, browse, glossary, classifications (read), asset detail, Alation migration.
  • Governance Portal — Command center for posture, workflows, queues. Phase 2; deep-links to Navigator for asset context.
  • Access Manager — Platform access workflows; integrates with governance classifications.
  • Foundations OMS UI — Engineer / technical path only — not a substitute for Navigator.

Answer “Read ?” → Yes. OMS projects governance metadata; governance repository remains tool-agnostic and Data Governance–aligned.
