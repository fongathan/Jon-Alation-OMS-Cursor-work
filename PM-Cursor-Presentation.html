PMs Using Cursor

Wireframes, POCs & Reports — Without Waiting on Engineering

How Product Managers can turn specs into shareable artifacts in minutes, validate ideas faster, and de-risk before we commit engineering time.

Context

The bottleneck we're solving

PMs often wait for design or engineering to visualize an idea

  • Wireframes: Need design time or Figma skills
  • POCs: Need engineering bandwidth to validate feasibility
  • Reports: Need scripts, dashboards, or manual data wrangling

Cursor lets PMs generate these artifacts themselves — not to replace engineering, but to validate and communicate before we commit.

How it works

PM input → Cursor → Artifact

I wrote the requirements; Cursor generated the code. I iterated on prompts.

Example prompt (Kronos wireframe):

"Create a standalone HTML dashboard for an OMS-style inventory tool. Include: sidebar nav (Dashboard, Search, Vendors, Trackers, Systems, Use Cases, Register Asset, Relationships, Reports, Legal Exceptions), stat cards for counts, dark theme with Tailwind. Use Alpine.js for interactivity. Load data from a JSON file."

Example prompt (Alation dashboard):

"Build an HTML dashboard that reads from data.json. Show MAU, searches, top users, curation trends. Use Chart.js. Dark theme, executive-style. Include a Python script that fetches from Alation REST API and writes to data.json."

Practical Tips on Using AI as a PM

Five tips that make the difference

These practices improve output quality and save time

1

Use screenshots and pictures

Paste UI mockups, OMS screenshots, or reference images into Cursor. A picture is worth a thousand words — and tokens.Example: Migration Plan used OMS screenshots for gap analysis.

2

Talk in simplest terms possible

Avoid jargon. Say "sidebar with 4 links" not "navigation component with hierarchical menu structure." Clear = better output.Simple prompts get better, more predictable results.

3

Add context when possible

Use @ to reference files, specs, or docs. "Match the style of @base.html" or "Use the data shape from @data.json." Context reduces back-and-forth.Cursor uses workspace context — give it something to use.

4

Reverse engineer requirements when needed

Have an existing UI or doc? Paste it and ask: "What are the requirements implied by this?" Use the output as your spec.Start from what exists, then formalize.

5

Use expensive tokens on planning, cheaper ones on execution

Use a capable model (e.g., Claude, GPT-4) for the initial spec, architecture, and tricky decisions. Use a faster/cheaper model for routine edits, formatting, and small tweaks. Optimize cost without sacrificing quality.Plan once with the best; iterate with the rest.

Transparency

Division of labor

Being clear about who did what

  • I provided: User flows, data structures, acceptance criteria, Alation query IDs, cron schedule
  • Cursor generated: HTML, CSS, JavaScript, Python scripts, Jinja2 templates
  • I iterated: 2–3 prompt rounds for layout, added SETUP.md for Alation dashboard, tweaked Kronos data model

This isn't "AI did it" — it's PM + AI collaboration. The PM owns the problem and the spec; Cursor accelerates the artifact.

Honest assessment

Where this helps — and where it doesn't

Good for:

  • Early-stage mockups and stakeholder alignment
  • Validating flows before design/engineering
  • Internal reports and dashboards with known data shapes
  • Documentation and project plans

Not a replacement for:

  • Design review and accessibility
  • Production-grade code, error handling, security
  • Real API integrations and data pipelines

The goal: de-risk and communicate faster, not ship to prod without engineering.
